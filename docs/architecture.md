## Purpose

How the system is structured: components, boundaries, data flow, and the rules that keep it that way. *Why* a structural choice was made lives in `docs/decision-log.md`; *what* the product does lives in `docs/goals.md` and the task specs.

## 1. System Overview

A single-line MES for 4.0 Printing Press 1. UNS Studio runs the raw-layer sim `fourzero_printing_press1` on Walker's MacBook Pro, the same machine that runs Docker and this repo, and publishes 16 tags over MQTT. The MES stack runs in Docker on that machine: CoreFlux is the broker, Ignition ingests the tags and runs the MES logic and visuals, and PostgreSQL holds the MES records. The planned design (MES §8) adds Maestrohub to unwrap, cast and route, Timebase for raw tag history and Timebase Atlas to model the plant for the AI agents; **none of the three is deployed yet** (INFRA-003, not specced). Ignition publishes MES results back to the UNS in the functional folders under `…/Press 1/` (DEC-007). The data flow is in `docs/mes_requirements.md` §8, confirmed by Walker on Oct 20.

**Broker cut-over (done 2026-10-20, DEC-004).** The sim publishes to this stack's CoreFlux (host `127.0.0.1:1886`). The old `coreflux-mqtt` container (host 1884, project `notus-dev`) is no longer in the path.

**Current ingest path (DEC-002; Maestrohub not deployed).** Ignition's MQTT Engine (server `MES Coreflux`, custom namespace `All`, subscription `#`, `jsonPayload: false`) subscribes to CoreFlux directly. Each topic becomes one String tag holding the raw envelope under `[MQTT Engine]40Printing/Dallas/Press Room/Press 1/…`. The `press1` project library unwraps and casts it (VIS-001). The topic root is `40Printing` (DEC-005). Stale `[MQTT Engine]4.0 Printing/…` tags may remain; never read them.

**MES tag tree (DEC-007, Oct 22).** The MES reads and writes a tag tree in Ignition's `[default]` provider at `40Printing/Dallas/Press Room/Press 1/`, never `[MQTT Engine]` directly. Edge folders (`PLC`, `Print Section`, `Unwind`, `Rewind`, `Tunnel Dryer`) mirror the 16 raw tags, typed and cast. Functional folders (`Work Order`, `Schedule`, `Downtime`, `Planned Stop`, `OEE`) sit beside them. MES code lives in a separate `mes` project library; `press1` and the VIS-001 view are unchanged. Design: `docs/ignition_tag_namespace.md`. Edge folders built by UNS-002: expression tags `cast(jsonGet({[MQTT Engine]…}, "value"))`, generated by `ignition/tags/generate_edge_tags.py` and pushed as 8.3 tag resource files into the gateway's `tag-definition/default/` (read only at gateway start). A 17th edge tag, `PLC/SampleTime`, carries the sim's sample timestamp (ENG-001).

**MES engine (ENG-001).** Project library `mes.engine` and gateway timer `mesTick` (2 s) read the 17 edge tags, de-duplicate on `SampleTime`, and hold ingest state in gateway memory (`getGlobals()['mes.engine.v1']`, lost on restart): meter deltas with restart handling, debounced state segments (all states), `run_start` (Setup → Running), `product_change`, `gap`. Each event is logged at INFO (`m.engine`). Later tasks plug in through `mes.engine.HANDLERS`.

**Work orders (WO-001).** `mes.workorder.on_tick` (registered in `HANDLERS`) attributes each Setup → Running run to the earliest Released order of that product (`ORDER BY released_at, work_order_id`), sets Running / Complete with status-guarded updates, writes absolute meter totals into `mes.work_order_run`, flags sim restarts, resumes or closes open runs after a gateway restart, and keeps runs with no Released order unattributed in memory. Pure `handle()` + `_SqlDb`; tested by `ignition/tests/replay_workorder.py`.

**Functional folders (UNS-004).** 42 tags under `Work Order/Active`, `Schedule`, `Downtime`, `Planned Stop`, `OEE`, `Product/<code>`. Rule: the record is in PostgreSQL → query tag (connection `mes`, `executionMode FixedRate`, 2 s; `Product` 60 s); the truth is in gateway memory → memory tag written only by the MES logic (`system.tag.writeBlocking`). One writer per tag; logic tasks write database rows, never query tags. Generator `ignition/tags/generate_functional_tags.py`; table in `docs/tasks/task_UNS-004_functional_folders.md`. Detection logic is the pure `step()`, tested offline by `ignition/tests/replay_engine.py` against the sim definition.

**MES handlers (Oct 22).** `mes.engine.HANDLERS = [_workorder, _schedule, _downtime, _oee]`, each pure `handle()` + `_SqlDb` I/O with its own versioned `getGlobals()` store (`mes.workorder.v1`, `mes.schedule.v1`, `mes.downtime.v1`, `mes.oee.v1`): `mes.workorder` (WO-001/003: attribution, status, manual actions), `mes.schedule` (SCHED-001/002/003: plan vs actual, readiness, override, reconcile; `Schedule/*` memory tags), `mes.downtime` (DT-001/002: fault events, Setup split into `Changeover` + `Changeover overrun`; `Downtime/*` memory tags), `mes.oee` (OEE-001: one `oee_interval` row per minute per product). `mes.ui` holds read-only shaping for the throwaway test pages `/mes/work-orders`, `/mes/schedule`, `/mes/downtime` (`Mes/Test/*`). Offline tests in `ignition/tests/` run under `python3 -I`. Still to build: OEE-002, DT-003, UNS-005 (publish via `system.cirruslink.engine.publish`, allowlist of 13 tags), VIS-002 (`/mes`), AI-001.

## 4. Module Boundaries and Rules

- The MES never publishes to sim topics. MES output goes only to the functional folders under `…/Press 1/` (`Work Order`, `Schedule`, `Downtime`, `Planned Stop`, `OEE`). The edge folders are never published.
- The envelope is unwrapped and every value cast once, at ingest.
- Meters are consumed as deltas; a drop to 0 is a sim restart.
- No raw samples in PostgreSQL. Timebase holds history.
- Ideal speed and scheduled changeover live only in `product_master`.

## 5. Local Infrastructure

`docker-compose.yml` (project `mes-workshop-2026`, INFRA-001) runs CoreFlux, PostgreSQL and Ignition. Maestrohub, Timebase and Timebase Atlas are added by INFRA-003. UNS Studio runs on the host, not in compose. Credentials live in `.env` (git-ignored); names only in `.env.example`.

Walker's Mac runs other stacks, so host ports are offset and every one binds to `127.0.0.1` only (DEC-003):

| Service | Host | In-network | Notes |
|---|---|---|---|
| `coreflux` MQTT | `127.0.0.1:1886` | `coreflux:1883` | The sim publishes here. Host 1883 is UNS Studio itself; 1884 is the old broker. |
| `coreflux` web UI | http://localhost:8084 | `coreflux:8080` | |
| `coreflux` API / websockets | `127.0.0.1:5004` | `coreflux:5000` | |
| `db` | `127.0.0.1:5434` | `db:5432` | DB `mes`, user `mes` |
| `ignition` | http://localhost:8089 | `ignition:8088` | Admin user `admin` |

**Ignition project in git.** `ignition/projects/mes-2026/` is bind-mounted at `/usr/local/bin/ignition/data/projects/mes-2026`. Designer saves land in the repo. Files edited on disk need the gateway's Projects → "Scan File System" button (8.3 does not watch the folder).

**SCADA trend buffer (VIS-001).** Raw Press 1 samples (2 s, 60 min cap), events and jobs live in `system.util.getGlobals()['press1.v2']`, on the gateway only. There is no historian, database or Timebase behind it. It is lost on a gateway restart, and nothing is sampled while the Mac sleeps.

Inside a container, `localhost` is that container: Ignition reaches the broker at `coreflux:1883`, never `localhost:1886`.

## 6. Startup / Shutdown

`docker compose up -d` / `docker compose stop` from the repo root. Ignition waits for `db` to be healthy. Never `docker compose down -v` without the lead's say-so (it deletes all volume state). Stopping CoreFlux interrupts the sim's publishing but does not restart the sim. UNS Studio is never stopped or restarted as part of stack startup or shutdown.

## 7. Known Limits

- One press only. No other lines, presses or upstream and downstream steps.
- No control of the press.
- Detection, not prediction: faults have no lead-in in the sim (`docs/sim_spec_press1.md` §11 rule 6).
- Classroom time compression: stops every 60 s, changeovers in seconds.
- Spaces in topic levels (`Press Room`, `Press 1`, `Print Section`, `Tunnel Dryer`) work in Ignition MQTT Engine (VIS-001). They are untested in Maestrohub and Timebase. The dot was removed from the root (DEC-005).
- A sim restart resets the counters and the loop.
- When the Mac sleeps or UNS Studio pauses, the feed stops: the engine logs a `gap` and records nothing for that time (seen Oct 22 21:03:51Z–Oct 23 02:45:02Z, no counter reset).
